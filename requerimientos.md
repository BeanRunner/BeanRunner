JobRunner — Project Brief Documento del proyecto — Programación de Sistemas Avanzados 2026B Propósito El cliente requiere una plataforma ligera para registrar, ejecutar, supervisar y controlar trabajos del sistema operativo en equipos Linux. El producto deberá demostrar programación de sistemas: procesos, señales, concurrencia, comunicación entre procesos, persistencia básica y comunicación en red. Objetivo del producto Entregar un JobRunner operativo que permita enviar comandos o programas como trabajos, ejecutarlos en segundo plano con concurrencia controlada, consultar su estado, recuperar su salida y solicitar su terminación. El servicio deberá admitir operación local y acceso remoto únicamente desde la misma red privada o mediante VPN. Usuarios y partes interesadas ● Usuario operador: envía y controla trabajos.  ● Administrador: configura límites y acceso de red.  ● Cliente académico: revisa cumplimiento, evidencia y calidad de ingeniería.  ● Equipo de desarrollo: diseña, implementa, verifica y mantiene el producto. Alcance incluido Servicio JobRunner para Linux; cliente de línea de comandos; cola y ciclo de vida de trabajos; ejecución concurrente; captura de stdout/stderr; consulta, listado y cancelación; persistencia mínima de metadatos; bitácora; interfaz de red privada; documentación, pruebas y evidencia reproducible. Fuera de alcance Ejecución a través de Internet público; interfaz web obligatoria; orquestación de contenedores; alta disponibilidad; facturación; ejecución distribuida entre múltiples servidores; autenticación empresarial. Cualquier ampliación deberá registrarse como alcance opcional. Los elementos indicados como “fuera de alcance” no son obligatorios y no formarán parte de la evaluación base. En particular, JobRunner no requiere una interfaz web: la interacción mediante cliente de línea de comandos es suficiente. El equipo podrá proponer funciones adicionales, como una interfaz web o el uso de contenedores, únicamente después de cumplir los requisitos obligatorios. Estas ampliaciones deberán documentarse como opcionales y no podrán sustituir, modificar ni retrasar las funciones requeridas del sistema. Restricción de red El servicio remoto deberá escuchar en una dirección configurable y aceptar conexiones solo desde localhost, la LAN autorizada o una VPN. No se permite exponerlo directamente a Internet. La demostración deberá incluir conexión permitida y conexión rechazada o bloqueada. Entregables Código fuente y archivos de construcción; README; guías de usuario y técnica; configuración de ejemplo; scripts y casos de verificación; matriz de trazabilidad; resultados finales; registro de decisiones y evidencia de revisiones. Supuestos Sistema objetivo Linux; herramientas libres disponibles; equipos en una red controlada; tamaño de carga académico; los comandos ejecutados pertenecen al usuario del servicio y no requieren privilegios elevados. Criterio de éxito El producto se considera exitoso cuando satisface los requisitos aprobados, 1. Supera la verificación formal. 2. Demuestra utilidad ante escenarios de usuario y puede ser instalado.  3. Operado y reproducido por un tercero con la documentación entregada. Control de cambios Toda ambigüedad, excepción o cambio de alcance deberá documentarse en un Issue y aprobarse antes de modificar la línea base de requisitos. Responsabilidad técnica del proveedor El cliente define las capacidades y restricciones observables del producto, pero no prescribe una arquitectura única. El equipo proveedor deberá tomar, documentar, verificar y defender las decisiones necesarias para satisfacer los requisitos. ● Elegir y justificar el lenguaje, arquitectura, modelo de concurrencia, IPC, persistencia, protocolo y estrategia de recuperación. ● Comparar al menos dos alternativas viables para cada decisión arquitectónica relevante. ● Registrar consecuencias, riesgos y evidencia técnica de la alternativa elegida. ● Conservar trazabilidad entre decisiones, requisitos, implementación y pruebas. Uso de herramientas de inteligencia artificial El uso de herramientas de inteligencia artificial y vibe coding está permitido. Sin embargo, ningún resultado generado se considerará evidencia de competencia por sí mismo. ● El equipo será responsable de comprender, revisar, adaptar y probar todo artefacto entregado. ● La frase “lo recomendó la IA” no constituye una justificación técnica. ● Durante las revisiones, cualquier integrante podrá ser requerido para explicar una decisión, diagnosticar una falla o realizar un cambio limitado. ● El código que el equipo no pueda defender o verificar se considerará trabajo no terminado. Nota: la finalidad no es restringir el uso de IA, sino evaluar la capacidad del equipo para ejercer criterio y asumir responsabilidad técnica. Cada RF deberá vincularse con uno o más casos de verificación y evidencia. Gestión de trabajos RF-01. El sistema deberá aceptar el envío de un comando o programa con sus argumentos y devolver un identificador único de trabajo. RF-02. El sistema deberá validar la solicitud y rechazar entradas vacías, mal formadas o no autorizadas con un mensaje útil. RF-03. El sistema deberá mantener una cola cuando no exista capacidad inmediata de ejecución. RF-04. El sistema deberá ejecutar trabajos en procesos separados sin bloquear la atención de nuevas solicitudes. RF-05. El sistema deberá permitir configurar un máximo de trabajos simultáneos y respetarlo. Ciclo de vida y control RF-06. El sistema deberá representar, como mínimo, los estados QUEUED, RUNNING, SUCCEEDED, FAILED y CANCELED. RF-07. El sistema deberá registrar tiempos de recepción, inicio y terminación, además del código de salida cuando aplique. RF-08. El usuario deberá poder consultar el estado y metadatos de un trabajo por su ID. RF-09. El usuario deberá poder listar trabajos con filtros básicos por estado. RF-10. El usuario deberá poder solicitar la cancelación de un trabajo en cola o en ejecución; el sistema deberá reflejar el resultado. Salida, persistencia y recuperación RF-11. El sistema deberá capturar stdout y stderr sin mezclarlos y permitir su consulta. RF-12. El sistema deberá conservar metadatos y resultados mínimos después de reiniciar el servicio. RF-13. Al arrancar, el sistema deberá recuperar el historial persistido y marcar coherentemente los trabajos interrumpidos. RF-14. El sistema deberá producir una bitácora de eventos operativos y errores con marca temporal e identificador de trabajo. Operación y configuración RF-15. El servicio deberá iniciar y detenerse de forma controlada, sin aceptar trabajos nuevos durante el cierre. RF-16. La configuración deberá permitir definir directorio de datos, límite de concurrencia, interfaz y puerto de escucha. RF-17. El cliente deberá ofrecer ayuda de uso y códigos de salida adecuados para éxito y error. Acceso remoto privado RF-18. Un cliente en otro equipo deberá poder enviar, consultar, listar y cancelar trabajos mediante un protocolo documentado. RF-19. El servicio deberá admitir operación local y remota sin cambiar la semántica de las operaciones. RF-20. El servicio deberá restringir el acceso remoto a una lista configurable de redes o direcciones permitidas de la LAN/VPN. RF-21. El protocolo deberá delimitar mensajes, identificar errores y tolerar lecturas o escrituras parciales. RF-22. El sistema deberá manejar desconexiones del cliente sin terminar el servicio ni corromper trabajos. Administración mínima RF-23. El servicio deberá rechazar solicitudes que excedan límites configurados y registrarlas. RF-24. El administrador deberá poder consultar un resumen de salud: servicio activo, trabajos en ejecución, en cola y errores recientes. Reglas de aceptación Un requisito funcional solo se considera cumplido si existe implementación, caso de prueba, resultado esperado, evidencia y estado PASS en la matriz de trazabilidad. Una demostración manual sin evidencia reproducible no sustituye la prueba. Condiciones operativas y situaciones de conflicto Los siguientes requisitos definen resultados observables. El equipo deberá decidir y justificar el mecanismo técnico utilizado para cumplirlos. ● RF-25. Cuando la cola alcance su capacidad configurada, el sistema deberá rechazar nuevas solicitudes de forma explícita, sin bloquear indefinidamente ni perder trabajos aceptados. ● RF-26. Dos solicitudes concurrentes de cancelación sobre el mismo trabajo deberán producir un estado final coherente y respuestas comprensibles para ambos clientes. ● RF-27. Una solicitud duplicada o reenviada no deberá crear estados contradictorios; el equipo deberá documentar la semántica elegida para identificar o tratar duplicados. ● RF-28. Si un cliente se desconecta durante una solicitud, el servicio deberá conservar un estado coherente y documentar si la operación fue aceptada, rechazada o quedó sin efecto. ● RF-29. Si un proceso hijo termina inesperadamente, el servicio deberá detectar el evento, liberar sus recursos y registrar un estado terminal con información de diagnóstico. ● RF-30. Si un trabajo no termina después de la solicitud normal de cancelación, el sistema deberá aplicar una política de escalamiento documentada y verificable. Decisiones funcionales obligatorias Antes de implementar, el equipo deberá establecer y documentar la semántica de los siguientes comportamientos: ● Capacidad máxima de la cola y respuesta ante saturación. ● Tratamiento de solicitudes duplicadas. ● Resultado de trabajos en cola y en ejecución después de reiniciar el servicio. ● Política de cancelación, tiempo de espera y escalamiento. ● Retención y eliminación de resultados. ● Soporte para múltiples clientes simultáneos. Consistencia, recuperación y presión de carga Estos requisitos establecen propiedades observables y dejan al equipo la selección de mecanismos concretos. ● RNF-27. Las transiciones de estado deberán ser consistentes ante solicitudes concurrentes; no se admitirán combinaciones imposibles o regresiones de estado. ● RNF-28. Las actualizaciones persistentes deberán ser atómicas o recuperables; una interrupción durante la escritura no deberá dejar el repositorio de datos inutilizable. ● RNF-29. El sistema deberá aplicar backpressure o rechazo explícito cuando alcance sus límites de cola, memoria, descriptores o clientes. ● RNF-30. Después de un cierre o falla, el servicio no deberá dejar procesos huérfanos bajo su responsabilidad. ● RNF-31. La recuperación deberá distinguir trabajos pendientes, terminados e interrumpidos sin reportar ejecución inexistente. ● RNF-32. El protocolo deberá definir compatibilidad de versión y rechazar mensajes incompatibles de forma explícita. ● RNF-33. Las pruebas de estrés deberán demostrar liberación de memoria, procesos, archivos y sockets al concluir. ● RNF-34. Toda decisión que modifique seguridad, consistencia o recuperación deberá incluir análisis de riesgo y prueba asociada. El equipo podrá elegir archivos, SQLite u otra persistencia; procesos, hilos o multiplexación; y el formato de protocolo que considere adecuado, siempre que documente alternativas, consecuencias y pruebas. Métodos de verificación PRUEBA: ejecutar el sistema con entradas y condiciones controladas y comparar resultados. ANÁLISIS: revisar cálculos, arquitectura, código o datos para demostrar una propiedad. INSPECCIÓN: comprobar directamente archivos, configuración, documentación o estructura. DEMOSTRACIÓN: observar una operación representativa ante el cliente; complementa, pero no reemplaza, pruebas reproducibles. Niveles de prueba Unitarias: módulos y funciones aisladas.  Integración: procesos, IPC, persistencia y red.  Sistema: flujo completo cliente-servicio.  Robustez: fallos, límites y desconexiones.  Seguridad: exposición, validación y autorización de red.  Aceptación: escenarios de usuario sobre una versión candidata.
